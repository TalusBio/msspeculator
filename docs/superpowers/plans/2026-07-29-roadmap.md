# pepdistill roadmap — 2026-07-29

Consolidates what was scattered across memory notes, spec "Open" sections, and session
messages. Gitignored, like every other plan here.

**Direction update — 2026-08-02.** ONNX is deferred. The next product milestone is no longer
"raise one pooled validation number"; it is: report validation separately for every source,
generate a search-engine-ready spectral library from a small FASTA, and prove that library in
an actual search. Model scaling remains useful, but search performance is the acceptance test.

## The question that gates everything

Can a library generated by pepdistill recover useful peptide evidence in a real search? A pooled
spectral angle cannot answer that. At 0.7075 (2026-08-01, 132K params), the model is not yet a
convincing library generator, but that aggregate is also dominated by the largest validation
pool and hides source-specific failures. A prior note records 0.82 from "real data + longer",
but the configuration behind that number is not recorded, so it is a hint, not a target we know
is reachable.

The levers that matter most have still not been pulled: preset=base (899K params) has never
been run end to end, and the largest real-data run so far is 186K examples.

Track A improves and measures the model. Track D turns its output into the actual product and
is now the critical path. Track B is **done** as of 2026-08-01 — v2's terminal mods and the
multi-row RT affine are validated on real spectra. Track C is hygiene.

**All six is 338,734 examples**, ~271k after the 80% train split — **5.6x the single-shard

Otherwise as written: human + E. coli pretrain (~1.2M peptides, streams), preset=base (899K

## Track B — exercise what v2 built

v2 shipped terminal mods, mass-only mods, the two-encoder representation, and 18 newly
resolvable modification types. As of 2026-08-01, **B1 and B2 are done** — the
`runs/multipool10.toml` run put all of it through real spectra for the first time.

**B1. A TMT or PTM pool. — DONE 2026-08-01.** The run took four modified pools alongside the
unmodified one: `tmt/TMT_TUM_third_pool` (10 shards, TMT6plex terminal mods),
`test_ptm/Kmod_Acetyl` (2), `tmt_ptm/TMT_TUM_mod_imp_pSTY` (4, phospho stacked on TMT), and
`prospect/TUM_HLA` (2, non-tryptic). Every one decoded without a single `parse_modseq` failure.

Pairing TMT third pool with unmodified third pool was the point: same peptide population, so
modified-vs-unmodified is the only variable.

Terminal-mod encoding is now verified end to end on a **trained** artifact rather than a
synthetic parity fixture. Through the Rust CLI, `PEPTIDER` vs `[TMT6plex]PEPTIDER`:

```
b2^1 .. b7^1   every shared b ion   +229.162932   (TMT6plex monoisotopic, exact to 6 dp)
y1^1 .. y7^2   every shared y ion    +0.000000    (an N-term mod must not move the y ladder)
```

The central claim of v2 is no longer unvalidated on data.

Still unexercised: mass-only mods reached only via the CLI's bare-delta syntax
(`PEP[+229.162932]TIDER` runs, but no *training* example used the mass-only path), and most of
the 18 newly-resolvable types.

**B2. Two pools with different chromatography. — DONE 2026-08-01.** The run fitted **five**
ChromRunbook rows (`tmt_third_pool`, `third_pool_nomod`, `hla_immuno`, `kmod_acetyl`,
`tmt_phospho`), so scale+shift finally had to work across datasets rather than on one row.

Verified through the Rust CLI on the same peptide: iRT base 21.39, `tmt_third_pool` 22.66,
`hla_immuno` 25.37 — named rows resolve and differentiate. MS2 intensities are *identical*
between those two rows, which is the design working: `chrom_context` feeds only the RT head,
`ms_context` feeds MS2.

Caveat carried from the metric section: HLA/acetyl/phospho have ~112 val examples between them,
so their per-dataset RT quality is not yet measurable. B2 is demonstrated, not quantified.

**B3. Mutation augmentation.** Re-encode a residue as a lighter one plus a composition delta
(V ≡ A + C₂H₄; the single-CH₂ pairs are D→E, G→A, N→Q, S→T, V→I, V→L). Same molecule, same
target spectrum, so it forces `token + Δ` additivity — the core hypothesis of the whole
representation. Prerequisites, both real:
- `RESIDUE_COMPOSITION` (deferred from the v2 spec explicitly for this)
- a third `ModSpec` variant, `Delta { comp, mass }` — a mutation Δ has a composition but no
  UNIMOD identity, so it is neither `Named` nor `MassOnly`. The same variant serves the
  deferred "caller-supplied composition" item.
Wants a short spec: re-encode direction, probability, and whether it applies to the teacher
path, the real path, or both.

invisible to the KB-sized test fixtures: a dictionary/RLE-encoded parquet column read as one

that is 226 bytes on disk; the streaming reader's `ion_type`/`neutral_loss` cost 352 MB per row
group instead of 50 MB. Both fixed with `read_dictionary=`. **A3 is unblocked.**

## Landed 2026-07-31 — `streaming-multipool-train` (28 commits, base `867d2fb`)

Streaming multi-pool real-data training. Suite 133 → 211 passed / 1 skipped; rust 51 unchanged.
Spec: `docs/superpowers/specs/2026-07-31-streaming-multipool-train-design.md`.
First real run 2026-08-01: `runs/multipool10.toml`, logs under `runs/multipool10/`.

Shards extract once to local parquet; meta is read projected and `raw_file`-filtered once per
run; train streams row-group by row-group with per-spectrum acquisition factors; val is a
meta-derived winner allowlist; `[[train.sources]]` with per-source `instrument` and `val_only`.

**Two live defects on `main` were fixed in passing:**
- Acquisition factors were recorded once per raw file from its first spectrum. A PROSPECT raw
  file mixes them — one third-pool run is 15,325 ITMS against 14,649 FTMS with four NCE values
  — so ~18,500 spectra per shard carried a fabricated analyzer straight into `MSContextEncoder`.
  Every real-data run before 2026-08-01 trained on that.
- A shard's `raw_file`s are not derivable from its filename (third-pool shards hold three, none
  matching the stem; TMT shards hold one that does). Now read from the column.

**Two deliberate behaviour changes — numbers before and after are NOT comparable:**
- Val dedup is `argmax andromeda_score`, not summed matched-fragment intensity. Measured more
  representative (leave-one-out cosine to consensus 0.9374 vs 0.8871 over 300 keys,
  p = 1.36e-17). This changes the val set, so `val_spectral_angle` across this branch is a
  different measurement, not a better or worse one.
- Training uses the **train split only**. The old `fit_realspeclib` trained on `split != "val"`,
  i.e. it optimised on test. Test is now genuinely held out.

### Follow-ups this branch identified but did not do

**Register the dataset keys inside `ChromRunbook`.** The name→row map and the embedding rows are
maintained separately and must agree; a reviewer set `row = 1`, collapsing two pools onto one
chrom row, and every test passed — the artifact would advertise row 2 for a pool trained on
row 1. Store names in row order via `nn.Module.get_extra_state`/`set_extra_state` so they
serialize atomically with the weights. Blocked on it being a checkpoint-format change
(`registry._runbook_blob` + `export.py`'s ONNX v3 metadata), so it wants an artifact version
bump and its own spec. Cheap interim: assert each `ShardSpec.dataset_id == dataset_index[name]`.

**Delete the test-only decode path.** `to_labels`, `fit_realspeclib`, `_build_examples` and
`_dedupe_val` are now reachable only from tests, and they have already drifted from the
production path — `decode_fragments` still populates `RealLabels.acquisition` per raw file, the
exact fabrication this branch removed everywhere else.

**Consolidate the two RT-affine implementations.** `fit_realspeclib`'s inline cold-start block
and `establish_rt_norm` compute the same global affine by two independently written routes.
Numerically equivalent today; they apply different clamping (`set_norm`'s 1e-6 floor vs
`or 1.0`) and no test exercises both.

**Per-shard meta slices** when shard count grows. The meta index is the one structure that still
scales with it — 440 B/spectrum, so ~0.149 GB for third pool's six shards but ~5.94 GB at 500.
See the spec's "Known scaling limit" for the mechanism and the trigger.

Smaller, parked with reasons in the branch history: `extract_shard`'s basename cache key could
collide if one zip held two members with the same basename; the val shortfall log can be masked
when a `raw_file` spans two shards; the streaming/reference equivalence fixture covers train and
val but not test.

## Track D — FASTA to a searched spectral library (new critical path)

The generic Python generation path already exists:

`FASTA -> digest/mod-form/charge enumeration -> torch checkpoint inference -> long Parquet`

The Rust runtime now loads `.safetensors`, digests/enumerates a FASTA, predicts every precursor,
converts CCS to Bruker 1/K0, and writes a streaming DIA-NN TSV. Python/Torch is a parity oracle,
not the production generator. What remains is a search against genuine raw data and packaging
the reproducibility metadata.

**D1. Freeze the search contract — DONE 2026-08-02.** `timsseek_cli` 0.33.0; DIA-NN TSV;
engine-generated mass-shift decoys. Record the engine invocation, accepted
library schema, spectra input format, modification notation, RT units, intensity scale, decoy
responsibility, and required precursor/protein identifiers. Obtain the small FASTA, a small
representative spectra file, and a checked-in or scripted search configuration. Do not invent
an interchange format before inspecting what the engine actually consumes.

**D2. Implement Rust FASTA library generation and the engine adapter — DONE 2026-08-02.** Extended the Rust CLI/core
from single-peptide inference to FASTA parsing, digestion, modification/charge enumeration, and
multi-precursor prediction after loading the self-contained `.safetensors` artifact once. Emit
the engine's native library input from Rust. Keep engine-specific naming, column selection,
units, annotations, and serialization isolated from inference. Validate required columns,
finite values, precursor/fragment uniqueness, m/z ranges, and supported modifications before
writing. Test the Rust rows against Python/Torch on a tiny fixture, but generate the real test
library exclusively through Rust.

The supplied 461-protein FASTA generated 116,499 unique tryptic peptides, 474,630 precursors,
and 16,650,774 transitions. `timsseek` parsed all 474,630 elution groups in 7.2 seconds,
reported `sequence_features=Available`, and built 1,423,890 scoring entries after decoys.

**D3. Make library generation reproducible.** Add a Rust CLI entry point that takes the
`.safetensors` artifact, FASTA, digestion/modification settings, acquisition context, and engine target.
Write a manifest beside the library containing the model identity, FASTA digest, generation
parameters, precursor count, fragment count, and adapter version. ONNX and a Python runtime are
explicitly not prerequisites.

**D4. Run the engine end to end — DONE 2026-08-02.** Generated the library from the supplied
FASTA, invoked the supplied search engine on real spectra, and retained the
command/config/log/results.
The first acceptance gate is operational: the engine loads the whole library, the search
finishes, and reported matches map back to FASTA peptides with no schema/modification errors.
Then compare useful outcomes (identified precursors/peptides at the engine's chosen FDR, score
distribution, and failures by modification/charge) against a documented baseline library or
library-free run. Exact thresholds should be chosen only after the fixture and engine are known.

First real search: `timsseek` 0.33.0 against
`250225_Desnaux_200ng_Hela_ICC_on_DIA.d`, completed in 194.6 seconds. It reported 1,226 target
precursors / 1,105 unique modified sequences / 365 FASTA proteins at 1% FDR. Charge breakdown:
241 z=2, 929 z=3, 56 z=4. The observed 1/K0 was a median 3.47% below the CCS-derived library
mobility (5th–95th percentile -8.06% to +5.10%), so mobility conversion is functional but has
a measurable calibration bias. No baseline library or library-free result was supplied, so the
comparative-sensitivity half of this task remains open.

**D5. Feed search failures back into modelling.** Use per-dataset validation and search-result
strata together. Capacity/data experiments are justified by concrete weak strata (for example
TMT, a charge state, or a fragmentation context), not by movement in one pooled metric.

**D6. Optimize the production Rust inference path — IN PROGRESS 2026-08-02.** The original
single-core generator took 168.62 seconds for 474,630 precursors / 16,650,774 transitions.
Tensor views now avoid cloning safetensor weights, acquisition/chromatography projections are
prepared once, and the charge-independent transformer trunk plus RT head run once per modified
peptide rather than once per charge. The same workload now takes 68.06 seconds (2.48x faster,
6,974 precursors/s) with torch parity and transition counts unchanged. Batching all
charge-specific MS2/CCS heads into larger portable `matrixmultiply` GEMMs reduces that again to
65.09 seconds (7,292 precursors/s); Accelerate/CBLAS was rejected because a platform-specific
backend bought only another ~1.4% and changed one thresholded transition. Next evaluate true
same-length peptide batching. Bounded batches of 64 same-length modified peptides, with isolated
per-peptide attention but shared transformer/head projections, reduce the workload to 59.20
seconds (8,018 precursors/s) with scalar parity and transition counts unchanged. Leave ordered
parallel generation until its bounded-memory streaming design is explicit. A bounded worker pool
with immutable shared artifact weights, complete-batch result messages, and one writer now runs
the same `/dev/null` workload in 11.53–12.97 seconds (about 7 active inference cores, with
474,630 precursors and 16,650,774 transitions unchanged). The result channel preserves complete
precursor groups; global library order is intentionally unspecified.

The controlled Leaky ReLU training sweep also completed (same seed/data/60 epochs as GELU,
negative slope 0.01). Its weighted validation spectral angle was 0.7038 versus the GELU pooled
0.7075, but the real TIMS search was substantially worse: 122 targets at 1% FDR versus 1,226
for GELU, with only 94 precursor/charge identifications overlapping. Rust generation remained
within noise (11.86 s, 15,473,431 retained transitions versus GELU's 16,650,774), so the
activation substitution is not retained as a production change. The artifact and search outputs
are kept under `fasta_ignore/` for diagnosis.

The controlled tanh-GELU retraining sweep completed 2026-08-03 (same seed/data/60 epochs,
`nn.GELU(approximate="tanh")`). Its weighted per-dataset validation spectral angle was 0.7084
versus the exact-GELU pooled 0.7075. On the real TIMS search it produced 1,158 targets at 1% FDR,
1,644 at 5%, and 1,870 at 10%, versus GELU's 1,226 / 1,708 / 1,891; 713 precursor/charge
identifications overlapped at 1%. Rust generation was 8.54 s and retained 16,624,630 fragments
(GELU: 11.53–12.97 s and 16,650,774 fragments). Tanh-GELU is therefore a viable speed/quality
experiment. It is now the production default; exact GELU remains available for compatibility and
as the archived baseline.

## Parked, with reasons

- **Trainable runbook row 0 for iRT.** Declined 2026-07-29 *after* the frame fix removed its
  motivation (`train_irt` 0.049 — `rt_base` fits iRT unaided). Would cost the neutral-row
  invariant, undefine context-free inference for the CLI/artifact, and move the
  `rt_head`-vs-`a₀` identifiability ambiguity onto the anchor. Revisit only on evidence that
  iRT needs its own affine.
- **Unspecific windows in pretrain.** 5,268,074 windows on this proteome, ~2.7h, and
  `_round_robin` would end pretrain on a ~5.06M unspecific-only tail while we score on tryptic
  third pool. Enable when targeting non-tryptic data, with the window stream capped.
- **`a_d` identifiability regularizer.** `a_d` and `chrom_to_rt` can both express scale-ish
  effects through a nonlinear head. Only matters if reading `a_d` off a trained runbook becomes
  something we rely on.
- **Eval folds.** Sequence-hash split blocks run/mod folds; noted previously, unchanged.
- **Activation substitutions.** Keep trained tanh-GELU as the production default. Runtime-only
  substitutions are model-semantic changes: pure-Rust f32 `erff` changed thresholded output,
  while platform f64 `erf` is library-dependent. Leaky ReLU was rejected on the real search
  fixture (122 vs 1,226 targets at 1% FDR). A fully retrained tanh-GELU model is much closer
  (1,158 vs 1,226 at 1% FDR) and faster, so tanh-GELU is now the deliberate production choice;
  exact GELU remains available for compatibility and rollback.

## Suggested order

Superseded 2026-08-01. C1, B1, B2 and C5 are done; the original order assumed A1 first, but
the streaming branch made B1+B2 nearly free and they landed together.

What is worth doing next, in order:

1. **D1-D4: generate and search a small real library.** Use Rust loading `.safetensors`, the
   supplied FASTA, the supplied engine, and a small representative spectra file. This is the
   product milestone.
2. **preset=base, end to end.** 899K params against the 132K behind 0.7075, width-first per the
   arch sweep. Evaluate it by dataset and in the search fixture, not by one pooled headline.
3. **More data and a bigger val set.** `runs/modrep-v2-dia.toml`'s six shards are a long run
   rather than an OOM now. Scale by largest shard size. More shards per pool also buy unique
   validation peptides faster than merely adding more small pools.
4. **B3 mutation augmentation** — still the interesting modelling work, still needs
   `RESIDUE_COMPOSITION` and the `Delta { comp, mass }` `ModSpec` variant.
5. **Register the dataset keys in `ChromRunbook`** (see the landed-branch section) — now more
   valuable than it was, because runs carry five rows rather than one.

ONNX stays deferred until it solves a measured deployment constraint.
